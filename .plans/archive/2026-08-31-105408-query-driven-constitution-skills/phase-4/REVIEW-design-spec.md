# Lens: design-spec (design/spec consistency, test suite architecture, zero dependencies)

## Verdict: `approve-with-amendments`

## Blockers

1. **Hardcoded configuration assertions in test**
   - **Evidence**: `.plans/phase-4/PLAN.md:27` states the test should validate `last_updated ("2026-08-31")` and `version ("1.0.0")`.
   - **Why it is wrong**: Hardcoding transient values (like `last_updated`) as strict test assertions will cause the test suite to fail immediately when the constitution is routinely updated, breaking test suite maintainability.
   - **Fix**: Amend the plan to assert that `last_updated` and `version` match valid format regexes (e.g., `^\d{4}-\d{2}-\d{2}$` and semantic versioning), rather than literal string matching.

2. **Flaky metadata synchronization test due to case mismatch**
   - **Evidence**: `.plans/phase-4/PLAN.md:63` requires asserting that ADR markdown files in `ai-docs/decisions/` are registered under `decisions` in `ai-docs/constitution.yaml` with "matching shortcode ID and metadata." However, `ai-docs/decisions/ADR-0001-unified-esm.md:4` uses `- **Status**: Active` while `ai-docs/constitution.yaml:26` uses `status: "active"`.
   - **Why it is wrong**: A literal, case-sensitive matching implementation of this synchronization test will fail on the existing valid documents.
   - **Fix**: Explicitly specify that metadata matching (specifically for the status field) must be case-insensitive or normalized prior to comparison.

## Non-blocking

1. **YAML Parsing Strategy**: The plan explicitly forbids external npm dependencies like `js-yaml`, which correctly aligns with the zero-dependency goal. However, it does not specify *how* Subtest 1 and Subtest 4 should parse `ai-docs/constitution.yaml` for schema validation. A conformant but naive implementation might resort to brittle Regex string parsing. Consider explicitly suggesting `yq -o=json` via `child_process.execSync` to parse the YAML into native JavaScript objects for robust schema/key validation.
